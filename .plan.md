WHY OURS DOESN'T SHOW IN FULLSCREEN\n\nRanked by how likely each is to be the actual cause for this user. **The display-mode explanation is last, not first.**\n\n### The bugs in our window setup\n\n**(a) We set topmost exactly once, at creation, and never again.** `src/main/index.ts:153` calls `setAlwaysOnTop(true, \"screen-saver\")` while the window is still `show: false` (`:129`). The window is shown much later by `showInactive()` in `syncOverlayWindow` (`:190`). Nothing re-asserts topmost after that — not on show, not on lock/unlock, not on focus change, not on any timer. Windows z-order among topmost peers is last-writer-wins; when League takes foreground and restacks, a window that asserted `HWND_TOPMOST` minutes ago and has no re-assert mechanism loses. Discord re-asserts on **every foreground change** (`SetWinEventHook` → `SetWindowPos`); `electron-overlay-window` re-asserts on attach and on focus. We do neither. **This is the single most likely defect.**\n\n**(b) The `\"screen-saver\"` level is correct, but the comment above it is wrong and has been misleading us.** `src/main/index.ts:148` says it is *\"the highest level Electron offers.\"* On Windows there are no Electron levels at all: Chromium collapses them (`DesktopWindowTreeHostWin::SetZOrderLevel` — *\"collapsing the z-order enum into kNormal = normal, everything else = always on top\"*). The level string's **only** Windows effect is `behind_task_bar_`: `floating`, `torn-off-menu`, `modal-panel`, `main-menu`, `status` get pushed below the taskbar HWND; `pop-up-menu` and `screen-saver` do not. So `\"screen-saver\"` is the right value for the right reason (it is one of the two that skip the behind-taskbar `SetWindowPos`), and it buys us **zero** priority over any other topmost window. Keep the call, fix the comment. Also note the default is `floating` — never call `setAlwaysOnTop(true)` bare, and note that the constructor option `alwaysOnTop: true` takes the same default.\n\n**(c) `setVisibleOnAllWorkspaces(true, { visibleOnFullScreen: true })` at `src/main/index.ts:160` is dead code.** Electron's docs carry an explicit callout: *\"This API does nothing on Windows.\"* `visibleOnFullScreen` is macOS-only. This is the most dangerous line in the file, because it *looks* like the fullscreen fix and it is a no-op on our only shipping platform. Delete it.\n\n**(d) The overlay is nailed to the primary display and never follows the game.** `src/main/vensterplek.ts:59` special-cases `\"overlay\"` to `hoekVanHetSpel()`, which reads `screen.getPrimaryDisplay().workArea` (`:65`). Nothing in the repo reads an HWND, enumerates windows, matches a window title, or reads a process list. On a multi-monitor setup with League on the secondary display, **the overlay is on the wrong screen**, which the user reports as \"it doesn't show over the game.\" The file's own comment at `:55-58` asserts \"the game is on the primary display\" while `eerstePlaats()` at `:124-128` assumes the opposite for every other window and admits *\"there is no way from here to ask which monitor League is on.\"* Position is also computed once at creation and never recomputed — not on `display-metrics-changed`, not on re-show, not when the game starts.\n\n**(e) A visible overlay that is drawing nothing looks identical to a missing one.** `OverlayView.tsx:30` returns `null` when `!live || !live.isClassic`; `:35-36` returns `null` when there are no objectives, no empty trinket, and no skill order. A transparent, click-through, empty window with `isVisible() === true` is indistinguishable from an absent one in a bug report. We have no way to tell these apart today.\n\n**(f) Occlusion throttling — plausible, unmeasured.** We set no `webPreferences.backgroundThrottling`, and grep confirms **zero** `app.commandLine.appendSwitch` calls anywhere in the repo. Chromium's native window occlusion calculation is on by default (`BASE_FEATURE(kCalculateNativeWinOcclusion, base::FEATURE_ENABLED_BY_DEFAULT)`); a fullscreen game covering our overlay is *occluded*, not hidden, and that is a separate throttling path from `--disable-renderer-backgrounding`. Symptom would be a stale or blank overlay, not a missing one — i.e. it would present as (e). Cheap to rule out.\n\n**(g) Minor, but real: the lock state can drift.** `LiveView.tsx`'s local `ontgrendeld` is never synced from the `overlay:locked` broadcast, so the button label can disagree with `overlayVergrendeld` in main. Not a fullscreen cause; fix it while you are in there.\n\n### The display-mode reason, stated accurately\n\nIn **true legacy exclusive fullscreen** (a blt-model swapchain that has taken the output), the game owns scanout for that display and no external window composites over it, at any z-order, ever. One correction to the folklore: DWM is **not** \"switched off\" — `DwmEnableComposition` has been deprecated since Windows 8 (*\"DWM can no longer be programmatically disabled\"*). The output is simply bypassed.\n\nBut this is probably **not** what is happening to our user:\n\n- **League is DX11-only.** Riot removed DX9 in patch V14.9 (30 Apr 2024; announced in the V14.8 notes, 17 Apr 2024). DX11/DXGI is exactly the class **Fullscreen Optimizations** covers, and FSO *\"takes full screen exclusive games and runs them instead in a highly optimized borderless windowed format that takes up the entire screen\"* (Microsoft DirectX blog, 17 Dec 2019). When an overlay appears, *\"the DWM reassumes control of the display, and a slight performance overhead is incurred so that the overlay can be composited on top of the game in a safe and stable way.\"*\n- So a user only reaches genuinely unreachable exclusive fullscreen if FSO is **off** for `LeagueofLegends.exe` — most commonly because they ticked \"Disable fullscreen optimizations\" in the Compatibility tab, which Riot's own lag support article has historically told people to do. *(Medium confidence: that Riot page is a JS-rendered SPA and could not be fetched; the corroborating Riot Support tweet is from 2018.)*\n- **The symptom does not match.** A real FSE conflict is usually noisy, not silent: DXGI treats occlusion as first-class (`SetFullscreenState` returns `DXGI_ERROR_NOT_CURRENTLY_AVAILABLE` when the output window is occluded), and the observed behaviours are flicker, the game minimizing, or the game dropping to windowed. \"Your panel just isn't there,\" with no flicker and no mode change, points at (a)/(d)/(e), not at the swapchain.\n\n---\n\n## 3.
